# 14.4 Proceso (develope -> main + release/tag)

## Objetivo
Tener un flujo repetible y limpio:
- Se trabaja en `develope` con commits pequenos y auditables.
- Se prueba en servidor de pruebas.
- Cuando esta OK, se abre PR a `main`.
- El tag/release siempre apunta a lo que esta en `main` (produccion).

## Ramas
- `main`: rama estable y desplegable (produccion).
- `develope`: rama de integracion para cambios en curso (staging/pruebas).

Reglas:
- No hacer releases/tags en `develope`.
- Los tags (`vX.Y.Z-alpha.N`, `beta.N`, `rc.N`) se crean en `main` despues del merge.

## Flujo de trabajo

### A) Desarrollo en `develope`
1. Cambiar a `develope`.
2. Implementar cambios con commits siguiendo `tech_docs/14.2_spec_commits_conventional.spec`.
3. Si hay cambios user-facing:
   - Anotar en `CHANGELOG.md` en `[Unreleased]`.
   - Preparar la entrada en `assets/js/modules/whats-new.js` para la version objetivo (o dejarlo listo para el paso de release).
4. `push` a `origin/develope`.

### B) Pruebas (usuario/QA)
1. Desplegar `develope` en el servidor de pruebas.
2. Probar flujos criticos (login, listado, reproduccion, modales).
3. Si hay fallos:
   - Volver a A), corregir con commits pequenos, y repetir.

### C) PR y merge
1. Abrir PR: `base=main`, `compare=develope`.
2. Revisar el diff y aprobar.
3. Hacer merge a `main`.

### D) Release y tag (solo en `main`)
1. Actualizar version a la siguiente (por ejemplo `v0.1.0-alpha.4` -> `v0.1.0-alpha.5`):
   - `index.html`: `meta[name="app-version"]`
   - `README.md`: badge/tag de cabecera
   - `CHANGELOG.md`: mover items de `[Unreleased]` a la nueva seccion versionada
   - `assets/js/modules/whats-new.js`: anadir seccion `"vX.Y.Z-...": [...]` con mejoras user-facing
2. Commit en `main`:
   - `chore(release): vX.Y.Z-alpha.N`
3. Crear tag anotado:
   - `git tag -a vX.Y.Z-alpha.N -m "Release vX.Y.Z-alpha.N"`
4. Push:
   - `git push origin main`
   - `git push origin vX.Y.Z-alpha.N`

### E) Sincronizar `develope`
Despues del release, mantener `develope` al dia con `main`:
- Opcion recomendada: merge de `main` a `develope` (o fast-forward si aplica).

## Notas
- La regla clave: el tag debe ser una referencia fiable a lo desplegado en `main`.
- Si hay dudas de versionado, ver `tech_docs/versionado_semver.md`.
