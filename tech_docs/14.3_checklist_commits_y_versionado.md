# 14.3 Checklist (Commits, Versionado, Changelog)

## Para el autor (antes de abrir PR)

- [ ] Los cambios se han hecho en `develope` (no en `main`)
- [ ] Cada commit cumple `tech_docs/14.2_spec_commits_conventional.spec`
- [ ] Los commits estan separados por tema (sin mezclar cambios no relacionados)
- [ ] Si el cambio es user-facing: actualizado `CHANGELOG.md` en `[Unreleased]`
- [ ] Si el cambio es user-facing: actualizado `assets/js/modules/whats-new.js` para la version objetivo
- [ ] Si hay cambio de version/tag: se hara en `main` tras el merge (no en `develope`)
- [ ] Si hay breaking: incluido footer `BREAKING CHANGE:` y bump correcto segun `tech_docs/14.5versionado_semver.md`

## Para el revisor (durante review)

- [ ] El titulo/descripcion del PR se corresponde con los commits (no hay alcance oculto)
- [ ] Los cambios user-facing estan explicados en `assets/js/modules/whats-new.js`
- [ ] El `CHANGELOG.md` refleja lo que realmente cambia (sin marketing, sin inventar)
- [ ] No hay credenciales/token persistidos accidentalmente (revisar uso de localStorage)
- [ ] Las rutas de assets/imports funcionan en despliegue estatico (rutas relativas `./assets/...`)

## Para el release (despues del merge a `main`)

- [ ] `index.html`: `meta[name="app-version"]` actualizado a la nueva version
- [ ] `README.md`: badge/tag actualizado
- [ ] `CHANGELOG.md`: `[Unreleased]` vaciado y nueva seccion `vX.Y.Z-...` creada con fecha
- [ ] `assets/js/modules/whats-new.js`: nueva seccion `"vX.Y.Z-...": [...]` con cambios user-facing
- [ ] Commit en `main`: `chore(release): vX.Y.Z-...`
- [ ] Tag anotado creado y subido: `git tag -a ...` + `git push origin <tag>`
